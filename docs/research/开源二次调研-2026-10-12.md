### 三条不变（别因为①–⑤就动摇）

1. **没有任何公开数据集是"模型 ↔ 人画图纸（带标注）"的配对**。逐一核实 Zero-To-CAD 1M、Omni-CAD、Text2CAD、
   WHUCAD、ABC、Fusion 360 Gallery、ShapeTalk：全部只有模型/命令序列/文本，**没有图纸标注**。
   → **#45（取 30–50 张集团历史图纸）的优先级没有任何东西能动摇。**
2. **尺寸方案的合法性仍然是符号问题，开源数值求解器全都不做**。Frontier（需 Maple V，跑不起来）、
   ezpz（解后雅可比 QR 秩，PR#278 `rank()/redundant()` 至今未合并）、pygeosolve（实测：欠定**静默解出**、
   冲突留残差**不报错**）、NeoGeoSolver（`TestRank` 有 DOF 计数但**全仓零调用者**）。
   → 我们的 linter 不该换。**可搬的只有一件**：SolveSpace 用 `andFindBad` 逐条剔除约束重算秩来
   **点名是哪几条在打架** —— 我们现在能判超定但不指出哪两条尺寸冲突。本体 GPLv3+ 且需 cmake，不引入。
3. **标题栏/图框没有开源解**。GOST 那套（`CATIA-V5-GOST-TitleBlocks`）连 LICENSE 都没有，只能看形态：
   它用**实线=必填栏 / 虚线=可省略附加栏**表达"哪些格允许空着"，正是我们 GB/T 10609 那个未解决的
   56 vs 64 高度冲突旁边、我们缺的**组织方式**。→ #43「导入客户图框模板」仍排在「转录国标全表」之前。

## 3. 实测记录（我自己跑的，命令可复制）

### 3.1 DXF → DWG → 独立回读（**推翻"DWG 从未验证"**）

```bash
# 纯 cargo 构建产物（无 cmake、无 GPU），来自 /tmp/dwgscan/cadcraft
/tmp/dwgscan/cadcraft/target/release/cadcraft-cli convert \
    drawform/out/seat_three_view.dxf /tmp/verify_tv.dwg        # 0.33 s，23637 字节，头 7 字节 = AC1024
/tmp/dwgscan/libredwg-0.13.3/programs/dwgread /tmp/verify_tv.dwg -o /tmp/verify_back.dxf   # 打印 SUCCESS
```

同一份 venv 用 ezdxf 数两侧：源 **DIMENSION 14** → 往返后 **14**，文字逐条相同
（`80 / 52 / 50 / 2×⌀9 / ⌀20 / ⌴⌀32 / ⌀40 / ↧6`）。反向对照：`ezdxf.readfile('/tmp/verify_tv.dwg')`
→ `OSError: not a DXF file`，坐实它真是二进制 DWG 而不是改名 DXF。

**边界**：本机只能保证**字节级互操作**，不能替代在集团真 AutoCAD 里的肉眼验收。→ #76

### 3.2 STEP AP242 语义 PMI 读取（正向案例成立）

前提：我们的 65 件语料**全部**是 `AUTOMOTIVE_DESIGN { 1 0 10303 214 1 1 1 1 }`（AP214），
grep `DIMENS`/`GEOMETRIC_TOLERANCE`/`ANNOTATION_CURVE`/`MDA` **0 命中** → 语料里没有 PMI，
所以这条路的正向案例必须从外部来（`pmix` 的 NIST 夹具）。

```bash
spike/.venv/bin/python /tmp/myprobe_pmi2.py /tmp/pmi/pmix/tests/fixtures/nist/nist_ctc_04_asme1_ap242-e2.stp
# Transfer: True
# labels: dims=13 fcf=6 datums=15
```

踩到的绑定坑（**全部实测**，写下来省下一个人的时间）：
- 静态方法带 `_s`：`XCAFApp_Application.GetApplication_s()`、`DimTolTool_s()`；取根用 `doc.Main()`（不是 `MainSection`）。
- 出参是**填充式**，容器在 `OCP.collections.Sequence_TDF_Label`（`OCP.TDF` 里没有 `TDF_LabelSequence`）。
- **`XCAFDoc_DimTolTool` 只有 `SetDimension`，没有 `GetDimension`** → 取语义对象要走 `TDF_AttributeIterator` + `isinstance`。
- `DimensionObject` 上**存在** `GetValue / GetLowerTolValue / GetUpperTolValue / IsDimWithPlusMinusTolerance / IsDimWithClassOfTolerance / GetType`；
  **不存在** `HasLowerInclVal / GetDimensionType / GetUnitSystem / GetName`。
- **进程退出时 OCCT 静态析构会段错误** → 打完就 `os._exit(0)`。
- ⚠️ 待复核（后台探针在跑）：值级与 NIST CSV 真值的一致性、**"语义 PMI vs 图形-only"的分档**
  （已知危险：图形-only 文件能数出 60 条 presentation 但名义值全为 0 = 等于读不到）、
  以及 OCCT **静默丢实体**（CTC-04 里 `4×M12×1.75-6H` 的 Ø12，XCAF 丢了而 pmix 读到 → **不能只信一条 oracle**）。

### 3.2b 值级核对结果（探针跑完，关键数字我本人复跑过）

17 件 NIST AP242 全量：**A 档语义可读 16 件 / B 档图形-only 1 件 / C 档读不出 0 件**。
11 件有官方 CSV 真值的文件上，值级合计 **378/411 = 92.0%**（尺寸 117/128、形位公差 195/216、基准字母 66/67）。

我自己复跑确认的三件事：

1. **CTC-04 的语义是真的**（`/tmp/mine_ctc04.json`）：13 条 label 里 **9 条名义值非 0**
   —— `75.0`、`6.65±0.12`、`14±0.1`、`20±0.2`、`20±0.2`、`90±1`、`20±0.3`、`25±0.25`、`10.0`；
   6 条 FCF 全有值（Position Ø0.35 / Ø1.5 / Ø0.3，Profile 2.0 / 0.2 / 0.5）。
2. **图形-only 陷阱是真的，而且伪装度极高**（`nist_ftc_08_...-e1-tg.stp`）：
   `dim_labels=60`、`dims_with_object=60`，但 **`dims_nonzero_nominal=0`、fcf=0、datums=0**。
   → **任何 PMI 读取代码都必须以"名义值非 0"为准，绝不能数 label。** 这条要写进 #77 的验收判据。
3. **绑定细节补一条**（我踩的，子代理报告里没写清）：label 上的属性是 **`XCAFDoc_Dimension`**，
   语义对象要用它的 `GetObject()` 取出来；属性本身 `isinstance(XCAFDimTolObjects_DimensionObject)` **不成立**，
   而且该属性**没有 `GetTypeName()`**。我第一版探针因此 13 条全读成空 —— 差点把"能读"误判成"读不出"。

### 四个必须写进 #77 的坑（子代理实测；第 4 条我只在对称公差上复现，非对称例未复核）

| 坑 | 实测 | 后果 |
|---|---|---|
| **同文件内两套单位制** | 尺寸 nominal 与偏差换算成 mm（0.234″→5.9436），但 **ftc_09 的形位公差保持源单位**（`⊕\|∅.010` 读出 0.010 而非 0.254），而 **ctc_03 的公差却换算了的**（`.010`→0.254） | 不逐文件、逐 PMI 类别拟合比例，就会把公差**错 25.4 倍** |
| **XCAF 会静默丢尺寸** | 全库 pmix 266 条语义尺寸，XCAF 丢 **17 条（6.4%）**；CTC-04 的 Ø12 来自 `COMPOSITE_GROUP_SHAPE_ASPECT`（'Position.3' pattern），**完全是语义的**却丢了 | **不能只信 OCCT 一条路**，要 pmix 当第二 oracle |
| **丢的是散点不是规律** | 丢的 17 条里 11 条是复合特征、**4 条是普通 `SHAPE_ASPECT`**（ftc_08 的 ⌀0.228/⌀0.242 整批丢）；而同类 81/92 条是被读出来的 | "复合特征必丢"不成立 → 不能靠规则补，只能双源比对 |
| **label 计数严重失真 + 偏差符号不可靠** | 基准 label 87(ctc_02)/76(ftc_09) 对应真实基准 6/8 个；`GetLower/UpperTolValue` 返回**幅值**且顺序不守 ASME 语义 | 公差带宽度能拿，**± 方向不可靠**（需另找判据或只报带宽） |

### 顺带捞到一条"该标哪些"的真信号

`ftc_11` 是 **32 面的回转体**，它的真值图纸**只标 6 条尺寸**（`⌀63±0.5` 外径、`⌀32±0.3` 内径、
`1.925±0.08` 厚、`R1.5±0.04`、`R0.1 MAX`、`197.9 basic`）**且不逐台阶标直径**；
`ftc_09`（279×191×3 薄板，73 面）的孔位**不是逐孔坐标标注**，靠孔组定位。

### 3.4 数表逐格交叉校验（**我们自己跑的结果**）

```bash

# ISO 2768 逐格比对：一致 32，冲突 0，段缺失 0
```

ISO 286 段序不同（它 21 段含 >500 的大段，我们 13 段），可比段上**冲突 3 格**：

| 尺寸段 | 等级 | 它 | 我们 | i 公式复算 | 谁对 |
|---|---|---|---|---|---|
| (80, 120] | IT6 | 23 | **22** | 10i = 21.73 | **我们** |
| (120, 180] | IT6 | 27 | **25** | 10i = 25.22 | **我们** |
| (120, 180] | IT9 | 97 | **100** | 40i = 100.87 | **我们** |

→ 结论：`tolerance-identifier` 的 **ISO 2768 可以当我们的第二/第三源**（32 格全合），
但它的 **ISO 286 有错，不能引**。这正是"开源界没人愿意做转录校验"的实证 —— 连 MIT 许可、
929 条自测全绿的表也会错 3 格，而公差表差 1 μm 就是错标。

### 3.6 符号字形覆盖率（解释我们 PDF 出方框的根因）

拿 CC0 表的 29 个码位在本机 1113 个字体族上实测（子代理跑，结论与我方观察一致）：
`⌴ U+2334` 只有 **4** 族能画、`⏥` 5、`⌭ ⌯ ⌰ ⌖ ⏤` 4–5、`⌀` 10、`↧` 9；
而 `○ ∠ ∥ ◎ Ⓜ` 有 30–89 族。它的 `codepoint_dedicated_to_gdt` **预测不了覆盖率**
（⌴ 是 dedicated=yes 却只 4 族），所以**替代不了我们自己的字体扫描**，只当"该扫哪些码位 + 哪些是借用字形"。

## 3.8 `quiddity`（Apache-2.0）实测：它解掉了 GEO-019，并暴露我们贯通判据在**双向出错**

**许可证**：`gh api repos/pzfreo/quiddity` → Apache-2.0（我复核过），NOTICE 声明派生自同为 Apache-2.0 的
build123d-drafting-helpers。搬代码义务只有"保留声明 + 注明修改"。

### 它怎么解 GEO-019（**位置判据，不是我们试过的否定判据**）

`holes.py:524-535`：孔的"主体"取**从开口向内最窄的那一段**（`bore_i = min(..., key=diameter)`），
沉孔**只能来自开口到该段之间**的段；再加 `holes.py:388-390` 的"必须单调收窄，比已见更宽的那段是槽不是台阶"。
part_0047 的段栈 `⌴8 | ⌀70 | ⌀8` 走这条 → `bore_i=0` → 候选集为空 → **不发沉孔**。
我们试过的两种改法都是"否定判据"（看到某种形状就拒），会误杀 part_0033 的真实沉孔；
它是"取最窄段当主体"的**正向位置判据**，所以 part_0033 的 `⌴⌀72 SF ↧1` 照样发得出来。

### 它同时打穿我们的贯通/盲孔判据（**我自己跑生产代码复核过**）

我们的 `_open_ends` 用两端环带扇探针；它用**边邻接 + 解析面型**（`_cylinder_stacks.py:131-183`、`:232-333`），
其中 `:298-302` 对**圆角环面**有显式判据（`MajorRadius < d/2` 即"往里卷 = 底"）—— 正是我们 GEO-008 残留缺的那一支。

我用生产 venv 跑 `extract_features` + `find_counterbores`，与语料 `iso_labels.json` 的 callout 对：

| 件 | 语料标注（真值） | 我们（我本人跑出的） | 判定 |
|---|---|---|---|
| part_0048 | `⌀50 ±0,2 ↧53`（**盲**） | `(50.0, 53.0, THRU)` | ❌ 判成贯通 |
| part_0041 | `⌀8`（**无 ↧ = 贯通**） | `(8.0, 23.0, BLIND)` | ❌ 判成盲 |
| part_0039 | `⌀9 ↧3,2`（**盲**） | `(9.0, 3.2, THRU)` | ❌ 判成贯通 |
| part_0010 | `⌀4 ↧18,27`（**盲**） | `(4.0, 18.0, THRU)` | ❌ 判成贯通（同件的 `⌴⌀80 SF ↧3,2` 我们是对的） |
| **part_0047** | 只有 `⌀80`、`⌀8`，**无 ⌴** | 发出沉孔 `(70.0, 90.0)` = **`⌴⌀70 90`** |  **GEO-019 我自己复现了** |

**判据错在两个方向上都有**（既有把盲判成贯通、也有把贯通判成盲），所以不能靠"往一边保守"糊过去。
子代理另报全语料 78 个可配直径上两实现一致 92.3%、6 条分歧逐条查真值 **6/6 是它对我们错**；
我亲自复核了其中 5 条（上表），**part_0033 那条我没复核到**（我抓的标注片段里没出现 `⌀28 ↧11,5`，
我们的输出是 `(28.0, 8.0, THRU)` 与 `(80.0, 11.5, BLIND)`，看着是**深度归到了错的直径上**，
但没拿到完整 callout，先不下结论）。

### 它不如我们 / 搬不动的部分

- **回转体台阶层弱于我们**：`recognise_turned_steps` 全语料只发 18 个 step / 9 件，part_0033、part_0030 直接 0；
  我们在 17 件上拿到 ≥2 个外圆。
- **OCCT 版本是硬限定**：它声明 `build123d>=0.9,<0.12`，而 ≤0.12 全部 pin `cadquery-ocp-novtk<8.0`
  （pip 两次 `ResolutionImpossible`）。子代理用 `--no-deps` 强上 **ocp 8.0.1.1.0 + build123d 0.13.0**：
  `recognise_holes` 与 7.8 输出 **65/65 零差异**，但 `feature_census` / `recognise_section_recesses`
  **65/65 崩**（`_adjacency.py:966` 用了 8.0 已删的 `TopoDS.Edge_s`）。
  → **恰好是我们想搬的那一层能在我们版本上跑**，但这条要在我们自己环境里重验一次才算定。
- **它也不是完备判据**：合成件 `d6|d12|d8` 阶梯通孔，quiddity 编造出 `⌴d8 ↧4`
  （根因 `holes.py:359`：两端都开口时按"哪段更粗"选开口，是启发式）。
  → 搬判据时要**自己补一条"台阶两侧都压着更小同轴孔则拒"**，并把这件当回归用例。
- `#55` 的假设载体：`_dispositions.py` 的 `Outcome/ReasonCode/Disposition` 封闭枚举 + `_REASON_SPEC` 自校验，

  后者才是我们 `assumptions.py` 的职责 → **搬结构，不搬代码**。
